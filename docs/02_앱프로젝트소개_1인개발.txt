02 앱 프로젝트 소개 / 심사 자료
프로젝트명: Pleos CurbLink / 플레오스 커브링크
작성 기준일: 2026년 10월 25일
참가 형태: 개인 / 1인 개발

1. 앱 한 줄 소개

Pleos CurbLink는 음성 주문 요청과 매장 준비 상태를 차량의 주차·주변 감지·사용자 승인 조건에 연결하여, 지정 픽업 공간에서 하차 없이 상품을 수령하도록 지원하는 Pleos Connect 네이티브 앱이다.

2. 기획 배경

퇴근길 장보기와 차량 대상 배달은 주문 이후에도 도착 위치 확인, 직원 호출, 수령인 인증, 적재 공간 확인을 전화와 메시지로 조율한다. 자녀나 고령자가 동승한 차량에서는 수령을 위한 하차가 돌봄의 중단으로 이어지고, 매장 직원은 차량을 찾거나 준비된 상품을 들고 대기하게 된다.

일반 스마트폰 앱은 차량의 P단, 테일게이트 상태, 후방 작업 공간과 주문 상태를 직접 연결하기 어렵다. 거치대의 상품 목록과 인증 화면은 운전자의 시각·수동 조작을 요구한다. CurbLink는 차량 데이터로 조작 가능 시점을 판단하고, 주행 중에는 승인된 음성 경로의 짧은 요청·조회만 제공하는 방향으로 설계한다.

현대자동차 인카페이먼트는 이미 제휴 F&B 주문과 일부 드라이브 스루 수령을 제공한다. 본 프로젝트는 주문 기능의 재현보다 ‘매장 준비 → 지정 구역 도착 → 인계 조건 확인 → 고객 승인 → 차량 상태 확인’의 연결을 차별점으로 삼는다.

초기 문제 가설은 기존 수령 과정에서 주차 탐색 3분, 매장 왕복 4분, 대기·인계 3분이 발생한다는 것이다. 총 10분은 실측 평균이 아닌 비교 실험용 가정이다. 1인 개발 단계에서는 지인·잠재 사용자 5명 내외의 모의 과업을 통해 조작 오류와 이해도를 확인한다. 실제 시간 절감과 매장 운영 효과는 제휴 파일럿 확보 후 측정한다.

첫 운영 대상은 지정 인계 공간을 확보한 매장이다. 한강 등 야외 주차장과 일반 배달 서비스는 공간 운영기관의 허용 및 파트너 확보 후 확장한다. 임의 도로변 정차를 서비스 전제로 삼지 않는다.

3. 앱 주요 기능 및 차량 특화 요소

① Voice Commerce: 주행 맥락에 맞춘 주문 요청
Gleo AI의 허용된 앱 연동 경로를 통해 재주문·진행 조회·변경 요청을 구조화한다. 실제 재고와 금액은 매장 시스템이 결정하며 LLM은 결제·차량 제어를 직접 실행하지 않는다. 상품 탐색과 결제 인증은 정차 및 OEM UX 제한 해제를 확인한 뒤 수행한다. D단·차속 0인 신호 대기 상태에서도 잠금을 유지한다.
현재 APK는 음성을 녹음·인식하지 않고 운영자 패널에서 음성 의도를 주입한다. 추가 요청은 보류 및 취소까지만 제공하며, 변경 결제는 후속 범위다.

② Precision Rendezvous: 도착과 인계 가능 상태 분리
상용 설계에서는 차량 GPS·NaviHelper 기반 접근 확인, 제휴 구역의 UWB 또는 표식 기반 구역 식별, SVM·초음파 기반 작업 공간 확인을 결합한다. UWB 및 카메라 접근은 지원 하드웨어와 OEM 권한을 확보한 경우에만 사용한다. 디지털 키 UWB나 SVM 영상이 일반 앱에 개방되어 있다고 전제하지 않는다.
센서는 ‘확인 범위 내 장애물 미검출 / 장애물 감지 / 확인 불가’로 표현한다. 오염·역광·고장·데이터 만료 시 확인 불가로 처리한다. 초음파·카메라만으로 모든 보행자나 장애물을 감지한다는 보장을 하지 않는다.
현재 APK는 A-3 구역 수동 확인과 모의 센서 입력을 제공한다. 센서 만료 3초는 심사 시연에서 상태 변화를 보여주는 설정이며 실제 안전 임계값이 아니다.

③ Trusted Handoff: 주문별 인증과 사용자 승인에 의한 인계
테일게이트 요청 전 6개 사전 조건을 평가한다.
  1) 차속 0 및 최신 차량 상태
  2) P단 및 UX 제한 해제
  3) 센서 데이터 유효
  4) 확인된 범위에서 장애물 미검출
  5) 주문·버전에 연결된 직원 인증 유효
  6) OEM 제어 허용
위 조건과 지정 구역·주문 준비·닫힘 상태가 충족되면 승인 버튼을 활성화한다. 사용자의 클릭을 7번째 조건으로 받아 클릭 순간 조건을 다시 검증한다. 사용자 승인을 미리 저장해 두거나 원격 이벤트만으로 개방하지 않는다.
개방 요청, 열림 응답, 닫힘 및 수령 확인을 별도 상태로 관리한다. 응답이 없으면 자동 재시도하지 않는다. 차량의 기본 인터록과 끼임 방지 기능을 우회하지 않는다.
CarPay는 공식 결제 화면과 인증 절차를 사용하는 제휴 연동으로 설계한다. 지원 차량의 지문 인증은 OEM 내부에서 처리하며 앱은 카드·지문 원본을 취급하지 않는다. 차량 식별만으로 결제 동의를 대체하지 않는다.
현재 APK는 모의 결제 세션과 메모리 내 멱등성을 구현한다. 실제 결제·서명 검증·환불은 연결하지 않는다. 공조 및 테일게이트의 실제 제어도 OEM 승인 후 적용할 후속 범위다.

4. 주요 사용 시나리오

페르소나: 자녀와 함께 귀가하는 30대 직장인. 지정 픽업 공간이 있는 마트에서 장보기 상품을 수령한다.

[탑승 및 경로 설정]
P단에서 저장 주문과 금액을 확인하고 결제한다. 매장은 주문과 도착 예정 시간대를 받는다. MVP는 고정 장바구니·모의 결제로 흐름을 재현한다.

[주행 중 인터랙션]
D단으로 전환하면 상품 탐색·결제·직원 인증·개방 조작을 숨긴다. ‘우유 추가’ 요청은 보류 상태로 표시한다. D단·0km/h에서도 잠금은 유지된다. 실제 음성 경로의 적용은 Gleo 권한 확인 후 진행한다.

[목적지 접근 및 사전 알림]
매장은 준비 완료 이벤트를 전달한다. 고객은 지정 구역 A-3에 주차한다. 도착 사실만으로 트렁크를 열지 않고 P단·차속·UX 제한·센서·주문 상태를 대조한다.

[하차 및 물품 수령]
직원이 주문별 일회용 코드를 제시한다. 고객이 정차 중 코드를 확인하고 주변을 직접 확인한 후 개방을 승인한다. 장애물 감지나 데이터 만료가 있으면 요청을 보류한다. 열림 응답 후 적재하고 닫힘 및 수령 확인으로 완료한다. 정상 흐름에서는 고객이 하차하지 않는다.

시연 운영자 패널은 가상 차량과 매장 데이터를 주입하는 시험 장치이며 운전자용 제품 화면이 아니다. 실제 AAOS의 주행 제한을 우회하지 않는다.

5. 개발 계획

1인 개발 범위: 외부 서버 없이 실행되는 AAOS 호환 네이티브 데모를 우선 완성한다. 복잡한 상용 서버·POS 연동 대신 로컬 매장 이벤트 처리로 핵심 상태 전이를 검증한다. 브라우저 프로토타입을 별도로 만들기보다 Android 앱 자체를 검증하고 녹화해 중복 구현을 줄인다.

아키텍처:
  Compose UI → ViewModel/StateFlow → 주문·인계 상태 관리
                               ├→ 인터록 평가기
                               ├→ 모의 결제 어댑터
                               └→ 매장 이벤트 검증기
  향후 차량 어댑터 → Pleos SDK/허용된 Car API → Car Service/OEM 서비스 → VHAL/차량 제어기
  향후 파트너 어댑터 → REST API/MQTT over TLS → 매장/POS/CarPay

기술 스택: Kotlin, Jetpack Compose, Coroutines/StateFlow, ViewModel, Android SDK. Car App Library는 앱 카테고리와 Pleos 호스트 호환 확인 후 필요 시 적용한다. 일반 앱이 VHAL 또는 CAN에 직접 접근하지 않는다.

권한 확인: Vehicle SDK의 상태 읽기·제어 권한, CarUxRestrictionsManager, 위치·경로 API, SVM·초음파·UWB, Gleo 앱 호출, CarPay 파트너 절차를 개별 확인한다. 확인 전 실제 연동 완료로 표기하지 않는다.

시연 검증: 주행 잠금, 신호 대기 잠금, P단 해제, 센서 만료, 장애물 진입, 권한 거부, 중복 결제·이벤트 방지, 정상 승인 및 인계. 경계 시각·미확인 값·주문 불일치·잘못된 이벤트·중복 개방 요청도 단위 시험한다.

운전자 주의 분산: NHTSA 시각·수동 조작 가이드의 시험 원칙 및 OEM/AAOS UX 제한에 맞춰 검증한다. NHTSA 가이드는 자발적 권고이며 음성 사용만으로 준수를 입증할 수 없다. 현대차 내부 기준과 실제 차종 시험은 출시 전 관문이다.

일정:

6. 기대효과 및 발전 가능성

기술 목표: 정의한 금지 조건의 테스트에서 앱 개방 요청을 차단하고, 동일 주문의 재시도에서 중복 모의 청구가 발생하지 않도록 한다. 이 목표는 시험 범위의 결과이며 실차 무사고 보장이 아니다.

파일럿 목표: 제휴 확보 후 고객 30명·매장 1~2곳에서 도착 후 수령 시간 중앙값 30% 감소, 위치 확인 연락 50% 감소, 직원 총 처리 시간 증가 없음 여부를 검증한다. 현재 이용자 확보 또는 실측 결과로 제시하지 않는다.

출시 12개월 사업 가정: 지원 차량·고객 10,000명에 접근 가능한 파트너를 확보할 경우 가입률 15% × 월 실제 이용률 40%로 MAU 600명을 목표로 한다. MAU는 월 1회 이상 수령 완료 기준이다. 월 3회 이용 시 1,800건, 객단가 20,000원 시 거래액 3,600만 원이다. 2% 플랫폼 수수료 가정 시 월 매출 72만 원이며 비용 차감 전 금액이다. 매장 운영 도구 구독을 추가하되 초기 1인 운영의 인건비를 충당한다고 과장하지 않는다. 파트너 지원과 운영 확장이 필요한 모델이다.

Retention: 첫 수령 후 30일 내 재수령률 30%를 목표로 저장 주문, 정확한 준비 알림, 지정 공간 확보를 개선한다. 주행 중 판매 유도 알림은 사용하지 않는다.

SDV 기여: Pleos App Market에서 차량의 상태·권한·사용자 승인을 결합한 실제 생활 서비스 사례를 제공한다. SDK 확대 시 어댑터를 교체할 수 있도록 도메인 로직을 분리한다.

PBV 확장: ST1의 물류 인계·적재 확인, PV5 Cargo의 다점포 픽업·공간별 인계에 적용 가능성을 검토한다. 각 차량의 OS·API·도어 형식이 같다고 가정하지 않으며 차종별 어댑터와 검증을 적용한다.

글로벌: 북미 커브사이드 리테일과 유럽 예약 수령 매장을 파트너 후보로 삼는다. 현지 결제, 데이터 처리, 공간 운영 규칙, 지원 하드웨어를 모듈화한다. 우선 한 개 파트너·지정 구역에서 반복 가능한 운영을 입증한다.
