# CurbLink Drive 기획서

차량용 앱 개발 공모전 제출용 기획서 원문입니다. 공식 접수 양식(DOCX)의 항목에 맞춰 옮겨 씁니다.

- 작성 기준: 2026-11-15, 앱 0.5.2 (release APK)
- 참가: 개인 · 이창환 · 일반 부문
- 저장소: https://github.com/leechanghwanspace/Pleos-CurbLink

표기: **[구현]** 현재 APK에서 동작하는 기능, **[계획]** 앞으로 할 일, **(가정)** 근거 자료 없이 세운 추정치.

---

## 1. 서비스 개요

| 항목 | 내용 |
|---|---|
| 서비스명 | **CurbLink Drive** |
| 한 줄 소개 | 주행 중 차량 상태를 읽어, 도착 이후의 식사·편안한 하차·현장 인계를 안전하게 미리 준비하는 차량용 앱 |
| 분야 | 모빌리티 라이프 케어 · 패밀리·동승자 케어 · 안전 운전 |
| 개발 플랫폼 | Pleos Playground SDK (NaviHelper 3.0.5), AAOS CarService, Kotlin · Jetpack Compose |
| 테스트 환경 | Pleos Connect v2.1.0 에뮬레이터 (Android 14, 2560×1440) |
| 산출물 | release APK, 소스 코드(GitHub), 시연 영상 2편 (APK 실행 2분 49초 / 웹 주행 시뮬레이션 3분 48초) |

> 내비게이션은 "목적지까지"를 안내합니다. CurbLink는 **"도착한 다음"**을 준비합니다.

차에서 내리는 순간 생기는 문제들이 있습니다. 음식은 언제 받는지, 휠체어로 내릴 공간이 있는지, 상대방에게 정확히 어디라고 알려야 하는지. CurbLink는 남은 주행 시간과 차량 상태를 이용해 이런 일을 도착 전에 끝내 둡니다.

## 2. 배경과 문제 정의

### 2-1. 문제

| 상황 | 겪는 문제 | 지금의 방식과 한계 |
|---|---|---|
| 퇴근길 식사 | 도착 후 주문하면 20~30분 대기, 미리 주문하면 음식이 먼저 와서 식음 | 운전 중 휴대폰으로 배달 앱 조작 → 안전 위험. 도착 시간과 조리 시간을 직접 맞춰야 함 |
| 교통약자 동승 하차 | 입구 바로 앞이라도 단차·경사·문 열 공간이 부족해 휠체어로 내리기 어려움 | 현장에 도착해서야 알게 되고, 다시 이동하거나 차도에서 무리하게 하차 |
| 주소가 불명확한 장소 | 한강공원·골목·대형 단지에서 배달원이나 일행에게 위치 설명이 어려움 | 전화로 반복 설명, 사진을 따로 찍어 보냄 |
| 도착 직전 차선 | 목적지 진입 직전에 급하게 차선 변경 | 경로 안내는 있지만 정차·진입 목적(픽업·주차·하차)에 맞춘 준비 안내는 부족 |

### 2-2. 핵심 니즈

1. 운전 중에는 손을 쓰지 않고 도착 이후를 준비하고 싶다.
2. 동승자의 이동 조건에 맞는 안전한 하차 지점을 미리 알고 싶다.
3. 계획대로 안 될 때(자리가 없음, 인식 실패 등) 바로 다음 행동을 알고 싶다.

위 문제는 기획 단계의 가설입니다. 실제 사용자 조사는 시범 운영에서 진행합니다.

## 3. 핵심 기능

### 3-1. 도착 안내 — 다음 차선을, 미리

- [구현] 1~4차선의 대기열·신호 대기·막힘 가능성·변경 횟수를 비용으로 비교해 추천 차선을 정합니다.
- [구현] 화면에는 **다음 행동 / 남은 거리 / 추천 차선 / 한 줄 이유**만 크게 보여 줍니다. 예: 다음 행동 "3차선 방향 변경 준비 · 표지와 안전 간격 확인", 이유 "2차선 대기 영향 · 직진 전용 추천"
- [구현] 비용 차이가 작으면 현재 차선을 유지하고, 차선 변경은 한 번에 한 칸씩만 안내합니다.
- [구현] 분기점 진입이 늦거나 변경이 금지되면 무리한 끼어들기 대신 재탐색을 안내하고, 정보가 없거나 만료되면 추천을 보류합니다.
- 차선·신호 정보는 현재 시험 입력입니다. [계획] 실제 교통 정보 연동.

### 3-2. 도착 맞춤 식사 — 당신과 음식이, 같은 시간에

- [구현] 남은 주행 시간과 메뉴별 "조리 + 배달 시간"을 비교해, 도착 시점에 맞춰 준비되는 메뉴부터 추천합니다.
- [구현] 주문은 도착 시간에 맞춰 예약되고, 예약 → 접수 → 조리 → 배달 → 도착 → 수령 순으로 상태를 보여 줍니다.
- [구현] 주행 중에는 **음성으로만** 추천·금액 확인·주문 확정을 합니다. "주문해줘"처럼 명확한 문장만 주문으로 인정하고, "하지 마"·"취소"가 들어가면 항상 취소로 처리합니다.
- [구현] 진행 중인 주문이 있으면 새 여정을 시작하지 못하게 해 주문 중복·분실을 막습니다.
- 매장·메뉴·주문은 견본 데이터입니다. [계획] 주문 플랫폼 연동.

### 3-3. 편안한 하차 — 가까운 입구보다, 편안한 하차

- [구현] 필요한 지원(휠체어 옆문 공간, 넓은 문 개방 공간, 완만한 경사, 직원 지원)을 고르면 후보 지점을 단차·차도 횡단·연석·경사·옆문 공간·직원 배치로 비교하고, 맞지 않는 곳은 이유를 보여 줍니다.
- [구현] 추천 지점이 막혀 있으면 "이 지점 이용 불가"로 제외하고 대안을 제시합니다. 맞는 곳이 없으면 조건을 완화하지 않고 "후보 없음"과 현장 도움 요청을 안내합니다.
- [구현] P단 정차 + 문 개방 공간 + 램프 준비 + 직원 수락이 모두 확인되어야 하차를 승인하고, 조건이 하나라도 바뀌면 승인을 자동으로 취소합니다.
- 시설 정보는 견본 데이터입니다. [계획] 공공 무장애 시설 데이터·시설 제휴 연동.

### 3-4. 현장 인계 — 주소 대신, 눈에 보이는 위치

- [구현] 전방·후방·좌측·우측 칸을 눌러 방향별 주변 사진을 고르고, 현재 GPS와 묶은 위치 카드를 공유합니다.
- [구현] 위치나 사진이 바뀌면 이전 공유 승인을 무효로 해서 잘못된 위치가 전달되지 않게 합니다.
- [계획] 차량 어라운드뷰(SVM) 영상으로 주변 사진 자동 생성.

### 3-5. 실패해도 다음 행동을 안내

- [구현] GPS·음성·사진·공유가 실패해도 진행 중인 주문과 사진은 유지하고, 다시 시도할 방법을 알려 줍니다.
- [구현] 실패를 이유로 주행 중 제한을 풀지 않습니다.

## 4. 차량 특화성 — 왜 휴대폰이 아니라 차량 앱인가

| 차량 앱이라서 가능한 것 | 휴대폰 앱의 한계 |
|---|---|
| 차량 기어·속도·UX 제한을 직접 읽어 주행/정차에 따라 조작 범위를 자동으로 바꿈 [구현] | 운전 중인지 알 수 없어 위험한 터치 조작을 막지 못함 |
| 내비게이션의 남은 시간·거리·도착 이벤트로 주문 예약과 하차 준비 시점을 맞춤 [구현] | 사용자가 도착 시간을 직접 계산해 입력 |
| 차량이 P단에 정차해야만 하차 승인 [구현] | 차량 상태와 무관하게 하차 안내 |
| 운전석 큰 화면에 다음 행동 하나만 크게, 나머지는 음성으로 [구현] | 작은 화면에서 여러 단계를 터치 |
| 차량 어라운드뷰 카메라로 주변 사진 자동 생성 [계획] | 사람이 내려서 직접 촬영 |

안전 설계 원칙
- 차량 정보가 끊기거나 5초 넘게 갱신되지 않으면 모든 조작을 막습니다. "모르면 막는다"가 원칙입니다.
- 화면에서 "동승자 조작"을 골라도 운전석 화면의 주행 중 제한은 풀리지 않습니다. 역할 선택은 권한이 아닙니다.

## 5. 기술 활용성 — Pleos Playground SDK·API

### 5-1. 활용한 SDK·API

| SDK / API | 사용 내용 | 앱 기능과의 연결 |
|---|---|---|
| NaviHelper 3.0.5 | 목적지 정보, 남은 시간·거리, 현재 위치, 도착 이벤트, 경로 취소·변경 이벤트 | 식사 예약 시점, 도착 판정, 위치 카드 좌표, 목적지 변경 시 이전 승인 폐기 |
| CarService – CarPropertyManager | 기어(GEAR_SELECTION)·속도(PERF_VEHICLE_SPEED)를 1초마다 읽음 | 주행/정차 판정, P단 정차 시에만 조작·하차 승인 |
| CarService – CarUxRestrictionsManager | 주행 중 UX 제한 상태 구독 | 제한 중 터치 입력 차단, 음성 경로로 전환 |
| Android 음성 인식·TTS | 음성 명령 입력, 안내 음성 | 주행 중 손을 쓰지 않는 주문 확정 |
| Android 시스템 사진 선택기 | 방향별 주변 사진 선택 | 위치 카드 사진 첨부 |

### 5-2. 검증 결과 (Pleos Connect v2.1.0 에뮬레이터)

| 검증 | 결과 |
|---|---|
| 실제 CarService·NaviHelper 연결·재연결 | 16개 조건 통과 |
| 외부 시험 드라이버 | 18개 흐름 / 94개 조건 통과 (시험용 관측 입력) |
| 규칙 단위 테스트 | 84개 통과 |
| release APK | 시뮬레이션·시험 코드 미포함, v2 서명, 16KB 정렬, release lint 오류 0 |
| release APK 실행 녹화 | 실제 차량 연결(P단)에서 24단계 진행 |

아직 확인하지 않은 것: 실제 경로·ETA 수신(시험 실행에서 `routeReady=false`), 실제 음성 인식·TTS, 공유 대상 앱으로의 실제 전달, TalkBack·로터리 입력, 실차.

### 5-3. 개발 방식

- 앱과 웹 주행 시뮬레이터가 같은 판단 규칙(차선·하차·식사)을 씁니다. 실제 도로에서 시험하기 어려운 픽업·주차·잠시 정차·식사·인계·배리어프리 여섯 여정을 웹에서 재현해 앱 규칙과 결과가 같은지 확인했습니다. 웹 시뮬레이터는 개발용 검증 환경이며 앱 UI가 아닙니다.
- 제품 APK에는 시뮬레이션·시험 코드를 넣지 않고, 빌드마다 자동으로 검사합니다.

### 5-4. 확장 계획 [계획]

- Gleo AI 음성 비서 연동: 대화형 메뉴 추천·주문
- 차량 어라운드뷰(SVM): 위치 카드용 주변 사진 자동 생성
- 도어·리프트 상태 연동: 하차 안전 확인 자동화

## 6. 사업성

### 6-1. 타깃 고객

| 구분 | 고객 | 겪는 문제 | CurbLink가 주는 가치 |
|---|---|---|---|
| 핵심 1 | 퇴근·장거리 이동 후 식사하는 운전자 | 도착 후 주문하면 대기, 운전 중 휴대폰 조작은 위험 | 남은 주행 시간에 맞춘 메뉴 추천, 주행 중 음성 주문 |
| 핵심 2 | 교통약자 동승 가족, 휠체어 사용자, 고령자를 태운 운전자 | 단차·경사·문 열 공간 때문에 하차가 어려움 | 조건 비교로 하차 지점 추천, 이용 불가 시 대안 |
| 확장 | 주소가 불명확한 장소의 배달·픽업 사용자 | 만날 위치 설명이 어려움 | GPS와 방향별 사진을 묶은 위치 카드 |

한국은 2025년 65세 이상 인구가 약 1,084만 명(전체의 21.2%)으로 초고령사회에 들어섰습니다. 고령 가족을 태우고 이동하는 운전자가 늘어나는 만큼 "도착 지점까지 편안한지"가 차량 서비스의 새 기준이 됩니다.

### 6-2. 시장 규모

| 구분 | 정의 | 규모 |
|---|---|---|
| 전체 시장 | Pleos Connect 탑재 차량 | 현대차그룹 목표: 2030년까지 약 2,000만 대 (확정치가 아닌 목표) |
| 진입 시장 | 국내 Pleos Connect 탑재 차량 | 2026년 신형 그랜저부터 적용. 탑재 대수는 아래 표의 가정치 |
| 초기 목표 | 탑재 차량 중 앱 설치 운전자 | 탑재 차량의 5~7% (가정) |

### 6-3. 예상 MAU (가정)

| 연도 | Pleos 탑재 차량 (가정) | 설치율 (가정) | 설치 수 | 월 활성 비율 (가정) | 예상 MAU |
|---|---|---|---|---|---|
| 1년차 (2027) | 국내 30만 대 | 5% | 1.5만 | 40% | 약 6천 |
| 2년차 (2028) | 국내 100만 대 | 7% | 7만 | 45% | 약 3.2만 |
| 3년차 (2029) | 국내외 500만 대 | 6% | 30만 | 45% | 약 13.5만 |

일부러 찾아 켜는 앱이 아니라 **목적지 도착이라는 반복 상황**에서 쓰이므로, 일반 모바일 앱보다 월 활성 비율을 높게 가정했습니다.

### 6-4. 리텐션

| 지표 | 목표 (가정) | 방법 |
|---|---|---|
| 30일 리텐션 | 30% | 자주 가는 목적지(집·회사·병원)를 기억해 도착 15~20분 전에 식사·하차 준비를 먼저 제안 |
| 90일 리텐션 | 25% | 필요한 지원 조건을 한 번 설정하면 계속 적용. 교통약자 가족은 대체 수단이 적어 이탈 동기가 낮음 |
| 주간 사용 빈도 | 주 2회 이상 | 출퇴근 식사 예약, 주말 가족 이동 등 반복 상황에 연결 |

실패해도 주문·사진을 유지하고, 주행 중에는 음성만 쓰게 해 이탈 요인을 줄입니다.

### 6-5. 수익 모델 [계획]

| 모델 | 대상 | 방식 | 시점 |
|---|---|---|---|
| 주문 중개 수수료 | 제휴 음식점·주문 플랫폼 | 도착 시간 맞춤 주문 1건당 수수료 | 2단계 |
| 시설 등록·데이터 연동 (B2B) | 병원, 공연장, 대형 상업시설, 주차장 | 배리어프리 하차 베이·접근 경로 등록, 연간 이용료 | 2단계 |
| 공공 협력 (B2G) | 지자체, 교통약자 지원기관 | 공공시설 무단차 하차 지점 데이터 연동 | 2~3단계 |
| 위치 인계 API | 배달·픽업·대리운전 서비스 | 위치 카드 수신 API 이용료 | 3단계 |

교통약자 하차 기능은 **사용자에게 무료**로 제공하고, 수익은 시설과 사업자 쪽에서 냅니다.

## 7. 사용자 시나리오

수치와 장소명은 앱의 견본 데이터를 사용한 예시입니다.

**A — 퇴근길 식사 (혼자 운전)**
1. 집을 목적지로 설정합니다. 남은 시간은 18분입니다.
2. 운전 중 "메뉴 추천해줘"라고 말하면 "조리 8분 + 배달 6분, 닭구이 덮밥 10,900원"을 음성으로 안내합니다.
3. "주문해줘"로 확정하면 도착 시간에 맞춰 예약됩니다.
4. 집 앞에서 P단으로 정차하고 수령을 확인합니다.

**B — 휠체어 사용 가족과 문화센터 방문**
1. 출발 전 "휠체어 옆문 공간"과 "현장 직원 지원"을 고릅니다.
2. 정문 앞은 계단·차도 횡단으로 제외되고 동측 무단차 베이 A-2가 추천됩니다.
3. 도착해 보니 A-2에 다른 차가 있습니다. "이 지점 이용 불가"를 누르면 북측 넓은 베이 A-3를 대안으로 제시합니다.
4. A-3에 P단 정차 후 문 개방 공간·램프·직원 지원을 확인하고 하차를 승인합니다.

**C — 한강공원 주차장 음식 인계**
1. 주소가 없는 강변 주차장에 도착합니다.
2. 전방·후방·좌측·우측 칸을 눌러 주변 사진을 고르고 현재 GPS와 묶어 위치 카드를 만듭니다.
3. 위치를 확인한 뒤 공유 앱으로 상대방에게 보냅니다.
